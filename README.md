# MultiSpace — Multi-Profile Browser (Android)

Every saved profile is an isolated browser environment (own cookies, localStorage,
IndexedDB, logins). Ten Instagram profiles = ten separate sessions.
Each profile can be pinned to the home screen as its own shortcut.

## Build

Requirements: Android Studio (Koala or newer), JDK 17, Android SDK 34.

1. Open this folder in Android Studio and let Gradle sync
   (it downloads Gradle 8.7 from `gradle/wrapper/gradle-wrapper.properties`).
2. Run on a device, or: **Build ▸ Build APK(s)**.
   Output: `app/build/outputs/apk/debug/app-debug.apk`
3. Command line (with the Gradle wrapper generated by Android Studio, or a local Gradle 8.7):
   `gradle :app:testDebugUnitTest :app:assembleDebug`
4. No local setup? Push to GitHub: `.github/workflows/build.yml` builds the APK and uploads it as an artifact.

Release APK: create `keystore.properties` in the project root
(`storeFile`, `storePassword`, `keyAlias`, `keyPassword`), then `gradle :app:assembleRelease`.
Without it, the release build is unsigned.

Requires a device whose WebView supports multi-profile (recent Chrome / Android System WebView).
If not supported, the app shows a warning and **refuses** to open profiles.

## How isolation works

* Engine: AndroidX WebKit multi-profile API (`ProfileStore`, `WebViewCompat.setProfile`).
* Each profile row has a random UUID. The engine profile name is `p_<uuid with _>`.
  The display name, color and icon are never used as storage identity.
* `BrowserActivity` creates a WebView, calls `setProfile(...)` before any navigation, then loads the URL.
  Same profile reopened → same engine profile → same login.
  New profile with the same URL → new UUID → new empty storage.
* Delete: `ProfileStore.deleteProfile(<that name>)` runs first; if the profile is still in use
  by a live WebView it throws and nothing is deleted (user is told to close the window).
  Only after that succeeds are the Room row and the pinned shortcut removed.
* Shortcut: `ShortcutManagerCompat.requestPinShortcut`, intent data `multinest://profile/<uuid>`,
  shortcut id `profile-<uuid>`. The launcher shows its own confirmation. Users can move shortcuts into launcher folders.
* Single activity with in-app tabs: one tab = one profile. A strip under the address bar switches between
  open profiles with one tap (e.g. 100 tabs, 100 Gmail accounts). Opening a profile that is already open just
  switches to it. At most 4 real WebViews are kept in memory; older tabs are released and re-created from their
  last URL when selected (login survives because cookies live in the profile storage, not in the WebView).
* Create many at once: "How many profiles to create" on the Add screen makes "Name 1 … Name N",
  each with its own UUID and its own storage (up to 9999 per batch, no limit in total; colors are assigned automatically, golden-angle hues, so they stay distinct).
* Shortcuts open the app (`singleTask`) and switch to / open that profile's tab.
* Downloads send only the current profile's cookies. SSL errors are not overridden (default = block).

## Engine decision

AndroidX WebKit multi-profile was chosen: system WebView (no ~60 MB engine), native per-profile cookie and
DOM-storage isolation, simple lifecycle. GeckoView (`contextId`) is the planned alternative if extensions become a priority.
Not verified on a device: see below.

How to run the isolation test on your phone:
1. Settings ▸ "Create 2 isolation-test profiles", open **Isolation test A** (httpbin sets cookie `who=A`, redirects to /cookies and shows it).
2. Open **Isolation test B**: it must show only `who=B`. Reopen A: only `who=A`.
3. Force-stop and relaunch the app, reopen A and B: values must persist.
4. Delete B (after closing its window): A must still show `who=A`.
5. Settings ▸ "Create 100 test profiles": check list scrolling and search.

## Not implemented / limitations

* One tab per profile (by design: a profile is a login identity). Two tabs of the same profile are not offered.
* Favicon not fetched; icons are built-in glyphs + color (custom hue).
* "Bookmark" sets the profile's start page; no separate bookmark list.
* Extensions / user scripts: not supported by system WebView. Roadmap: GeckoView WebExtensions
  (supports a subset of Firefox extensions on Android only, not Chrome extensions).
* sessionStorage is per page/tab by web standard and not persisted.
* Some sites block embedded browsers or require external sign-in; no bypass is attempted.
* Backups are disabled (`allowBackup=false`).

## MultiSpace 1.1.1 WebView compatibility update

This update keeps the existing AndroidX WebKit multi-profile storage model and stable profile IDs.
It enables third-party cookies per WebView, keeps modern web-app storage and image loading enabled,
allows user-initiated media to play without an extra browser gesture, and adds WebView/JavaScript
console plus main-frame/resource HTTP error logging. WebView remote inspection is enabled only in
debug builds. File and content URL access remain disabled, and mixed-content loading remains blocked.

No existing profile database or WebView profile storage is migrated, renamed, or deleted.
